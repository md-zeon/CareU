# Review, main, 2026-11-12

**Reviewed by**: opencode/big-pickle (author on Iceman)
**Scope**: 16 files, uncommitted
**Verdict**: Blocked

## Summary

This change lands the whole marketplace foundation from spec 0001: eight new Prisma schema files, the matching 1,400-line migration, a spec/verify pack, scope updates, and schema-contract tests. The structure is coherent and the migration is real (validated, applied, and drift-free), with genuinely good instincts around snapshots, append-only tables, unique idempotency keys, and scope anchors. The headline problem is that every money column is `INTEGER`/Prisma `Int`, which contradicts the repo's documented `bigint` poisha contract in `lib/money/` and caps amounts at ~21.5M BDT; behind that sit two incomplete financial snapshots (commission rate/basis, discount funding allocation) and cascade deletes that would destroy payment/refund/order history if anything ever deletes an order.

## Blockers

### 🔴 Money columns are 32-bit `Int`, contradicting the documented `bigint` poisha contract, `prisma/schema/catalog.prisma:117`
**Problem**: Every monetary column is Prisma `Int` / Postgres `INTEGER` (`listing_variant.pricePoisha` and `compareAtPoisha` at `catalog.prisma:117-118`; `order.prisma:17-21` totals and `89-94` line amounts; `payment.prisma:11, 55, 116, 141, 160, 184`). The existing money library defines `Poisha = bigint` and `isPoisha` returns true only for `bigint` (`lib/money/poisha.ts:18-23`), `lib/money/AGENTS.md` states "Every monetary column is `bigint` poisha ... store as `BigInt` Prisma columns (mapped from DB `BIGINT`)", and `lib/catalog/price.ts` repeats the rule. The same migration even uses `fxRateScaled BIGINT` (`order.prisma:14`) while amounts beside it are `INTEGER`, so the schema contradicts itself.
**Why it matters**: (1) `INTEGER` maxes at 2,147,483,647 poisha ≈ **21,474,836 BDT**, which a payout-batch total (`PayoutBatch.totalAmountPoisha`) or a large ledger/order can plausibly exceed, and it gives no headroom for future currencies. (2) Prisma will type every amount as `number`, so all domain code must convert at every boundary and `isPoisha` (and any `Poisha`-typed function) will reject database values; passing a raw `bigint` from `lib/money` to a write also fails without conversion. (3) Retyping money columns after any production data exists is one of the riskiest migrations possible. The new tests/verify doc compound it by explicitly asserting `Int` (`tests/marketplace-domain-model.test.ts:97, 111-135, 167, 175, 190`, `verify.md:6`).
**Suggested fix**: Make every `*Poisha` column `BigInt` (Postgres `BIGINT`) across catalog, order, payment, trust, and payout models, regenerate the migration before it ships, and update the schema tests/verify text to assert the `BIGINT`-backed shape. If the project consciously wants 32-bit storage, record that decision and reconcile `lib/money/AGENTS.md`, `poisha.ts`, and the `Poisha` type with it, plus add explicit range checks — right now the repo has two conflicting money contracts and neither the schema nor the spec says which wins.

## Major

### 🟠 Cascading deletes destroy payment, refund and order history, `prisma/schema/payment.prisma:6`
**Problem**: `Payment.order` and `Refund.order` use `onDelete: Cascade` (`payment.prisma:6, 50`), `Shipment.order`, `OrderItem.order` and `OrderItem.shipment` cascade (`order.prisma:46, 77, 79`), status history cascades, and the ledger's links are `onDelete: SetNull` (`payment.prisma:104, 108, 110, 112`). Deleting one `Order` row silently removes its payments, refunds, shipments, order items, status history, and every `FinancialLedgerEntry` loses its order/payment/refund linkage. AGENTS is explicit: "Never hard-delete rows that carry financial or audit obligations" and "Order lines, orders, refunds and settlements keep immutable financial snapshots". The author clearly knows `Restrict` matters (it is used for shop owners, order customers, listings, and payout items), so this looks accidental rather than deliberate.
**Why it matters**: No delete path exists today, but this is a loaded gun in the foundation. The first "delete order" daisy-cutter (admin cleanup, test fixture, future account/privacy task) will erase legally-required financial records without a database error, and orphaned ledger entries break settlement audits.
**Suggested fix**: Use `Restrict`/`NoAction` for `Order → Payment`, `Order → Refund`, `Order → OrderItem`, `Order → Shipment`, `Shipment → OrderItem`, and the order/shipment/status-history children. Keep `Cascade` only for genuinely disposable children (support messages, attachments). Treat orders as non-deletable and say so in the spec; if a ledger row must survive an order delete, keep its FK `Restrict` rather than nulling the linkage.

### 🟠 The commission snapshot cannot be audited or reproduced, `prisma/schema/order.prisma:93`
**Problem**: `OrderItem` snapshots `commissionPoisha` but not the rate or the base it was computed from. `lib/money/discount.ts:200-214` and `lib/money/AGENTS.md:30` state the effective rule must be snapshotted as `commissionRateBps` + `commissionAmount` (INV-28), and `commissionBasePoisha` is the per-line result the library already produces. There is also no `commissionRuleId`/rule snapshot, and `commissionPoisha` defaults to `0`, so a forgotten computation is indistinguishable from a legitimate zero-commission (first-party) line.
**Why it matters**: Commission is real money owed by sellers. Once an order is placed, a rate change or a disputed payout cannot be explained from the record; support/finance must recompute with today's rules, which INV-28/INV-42 forbid. The 0 default turns a missing computation into silent revenue loss rather than a failed insert.
**Suggested fix**: Add `commissionRateBps` (nullable while rates are pending) and `commissionBasePoisha` to `OrderItem`, optionally a `commissionRuleId` snapshot reference, and stop defaulting `commissionPoisha` so inserts must state it. Update the AC-6 test to assert the rate/basis snapshot, not just the amount.

### 🟠 Discount funding/allocation is not snapshotted on the order line, `prisma/schema/order.prisma:91`
**Problem**: Each `OrderItem` stores a single `discountPoisha`, and `Order` stores a single `discountPoisha` (`order.prisma:18`). The confirmed rule is that CareU-funded discounts do **not** reduce the seller commission base while seller-funded discounts do (`docs/scope`, AGENTS "Commission on discounted items"), and `lib/money/discount.ts` returns `careuFunded`, `sellerFunded`, `commissionBase` and `grossAmount` per line. None of that split, and no campaign/coupon reference, exists in the schema. Spec AC-6 requires "discount or tax snapshots on orders and lines" with "allocations snapshotted".
**Why it matters**: The money model cannot record who paid for a discount, so seller earnings, commission, refunds and campaign reconciliation become unverifiable and will be recomputed from mutable campaign rules or crammed into the unqueryable `metadata` JSON. This is precisely the cross-domain money rule the spec was written to protect.
**Suggested fix**: Snapshot the per-line split (`careuFundedDiscountPoisha`, `sellerFundedDiscountPoisha`, `commissionBasePoisha`) and the order-level totals, plus a campaign/coupon reference (or an explicit note that coupons are a later entity but the allocation fields exist now). Add these to the AC-6 test.

## Minor

### 🟡 A shop cannot represent "awaiting approval" and defaults to sellable, `prisma/schema/seller.prisma:59`
**Problem**: `ShopStatus` is `ACTIVE | PAUSED | SUSPENDED` (`enums.prisma:23-27`) and `Shop.status` defaults to `ACTIVE` (`seller.prisma:59`). The spec's shop transition section describes a "pending/approved context", and sellers must be approved before selling; `approvedAt` is nullable, so an `ACTIVE` shop with no approval is a valid row.
**Why it matters**: Default-ON is the wrong direction for a seller-approval gate. Any code path that creates a shop before admin approval immediately exposes listings and accepts orders.
**Suggested fix**: Add a `PENDING` (or `DRAFT`) status and make it the default, or require `status`/`approvedAt` to be set explicitly at creation. Keep `ACTIVE` a deliberate transition.

### 🟡 Only fulfillment transitions get an append-only history, `prisma/schema/order.prisma:11`
**Problem**: `OrderStatusHistory`/`ShipmentStatusHistory` are typed with `FulfillmentStatus` only (`order.prisma:113-141`). `Order.paymentStatus` changes (COD collected, refunded, cancelled) have no history, `SupportCase.status` has no history (`trust.prisma:43`), and `Notification.status` is a mutable enum overwritten in place (`trust.prisma:115`). Spec AC-3 requires preserved status history, AGENTS requires support case status history, and AC-7 asks for notification channel and status history.
**Why it matters**: Disputes and settlement checks routinely need to know *when* an order became paid/refunded or when a case moved. Only `PaymentEvent` covers gateway events; manual COD collection and refund-driven order status changes leave no timeline.
**Suggested fix**: Add a payment-status history table (or generalize the order status history to carry the status kind), a support case status history (append-only), and either notification delivery attempts or a status history table instead of a single overwritable column.

### 🟡 `WishlistItem` uniqueness does not work for the common case, `prisma/schema/customer.prisma:48`
**Problem**: `@@unique([wishlistId, listingId, listingVariantId])` cannot prevent duplicates when `listingVariantId` is NULL (Postgres treats NULLs as distinct), and the model allows a row where both `listingId` and `listingVariantId` are NULL.
**Why it matters**: "Wishlist" is user-visible state; duplicate hearts on a listing is a real bug, and a null-target row is meaningless.
**Suggested fix**: Model the wish target explicitly (e.g. require `listingVariantId`, or one of the two with a check constraint) and enforce uniqueness with partial unique indexes (`WHERE listingVariantId IS NULL` / `IS NOT NULL`).

### 🟡 Review uniqueness is per order item, not per purchased product, `prisma/schema/trust.prisma:22`
**Problem**: `@@unique([userId, orderItemId])` allows the same customer to review the same product once per purchase; `listingId` and `productId` are both nullable with no "at least one target" rule. The confirmed requirement is "one review per eligible purchased product".
**Why it matters**: Repeat buyers can multiply reviews/ratings for one product, which is the abuse pattern verified-purchase reviews exist to prevent, and a review with no target cannot render on a product page.
**Suggested fix**: Decide the authoritative product scope per policy and add a unique constraint for it (e.g. per user + listing, or per user + product), and require the target to be present.

### 🟡 Payouts cannot record the destination per seller or the batch approval, `prisma/schema/payment.prisma:140`
**Problem**: `PayoutBatch` carries `method` and `destinationRef` (`payment.prisma:139-140`) but `PayoutItem` (one per shop) has only `transactionReference`. A batch spanning several sellers cannot express each seller's bank/wallet destination. `PayoutBatch` also has no approver/reason fields despite AGENTS requiring payout batches to be "manual, admin-approved, reasoned and audited".
**Why it matters**: "Seller payout destination: bank transfer and mobile wallet (exact method recorded per payout)" cannot be satisfied for a multi-seller batch, so the audit of where money went is incomplete.
**Suggested fix**: Move/duplicate method and destination onto `PayoutItem` (keeping the batch-level defaults if desired) and add `approvedByUserId`/`approvedAt`/`reason` (or document that `AuditLog` is the sole record and add the approver there deliberately).

### 🟡 Ledger entries have no currency, `prisma/schema/payment.prisma:99`
**Problem**: `FinancialLedgerEntry` stores `amountPoisha` but no `currency`, while `Order`, `OrderItem`, `Shipment`, `Refund`, `Payment`, `PayoutBatch`, `PayoutItem` and `CODReconciliationRecord` all carry one.
**Why it matters**: The ledger is the money source of truth; the spec invariant explicitly requires currency snapshots on financial/settlement records and leaves room for non-BDT jurisdictions. An amount with no currency is uninterpretable.
**Suggested fix**: Add `currency` (integer minor units remain, currency column required) or, if BDT-only is a hard invariant for the ledger, say so in the model and spec and add a check that it matches the order currency.

### 🟡 Financial and workflow types are free-form strings, `prisma/schema/payment.prisma:115`
**Problem**: `FinancialLedgerEntry.entryType`, `direction`, and `eligibilityStatus` are `String` (`payment.prisma:115-118`); `Refund.method` is `String` (`payment.prisma:57`); `DeliveryAssignment.assigneeType` is `String` (`order.prisma:147`). Every other workflow in this schema uses enums.
**Why it matters**: The ledger's entry type and debit/credit direction are the core invariants of the money model; a typo or casing drift creates an entry that no reconciliation query will match. Free-form strings also prevent compile-time exhaustiveness in later slices.
**Suggested fix**: Use enums for ledger entry type, direction, eligibility, refund method, and assignee type (or validate them centrally at the data-access boundary and document the allowed values).

### 🟡 Financial mutations lack idempotency/dedupe protection, `prisma/schema/payment.prisma:47`
**Problem**: `Refund`, `PayoutItem` and `StockMovement` have no idempotency key or unique business key, `Order`/checkout has none (only `StockReservation.idempotencyKey` exists, `inventory.prisma:73-77`), and `Payment` has only a non-unique index on `(provider, providerReference)` (`payment.prisma:22`). AGENTS requires idempotency for orders, inventory, payments and refunds and "never apply a financial effect twice".
**Why it matters**: Double-clicked refund approval, a retried payout item, or a replayed movement can post two effects; duplicate gateway references can create two `Payment` rows for one transaction. Reservation-level idempotency does not stop a duplicate parent order.
**Suggested fix**: Add idempotency keys/unique business keys to refunds and payout items, an order/checkout idempotency key, a `StockMovement` reference uniqueness scheme, and a unique (or partial unique) index on `Payment(provider, providerReference)`.

### 🟡 No database checks for non-negative stock, prices or quantities, `prisma/schema/inventory.prisma:28`
**Problem**: `onHand`/`reserved` (`inventory.prisma:28-29`), `StockMovement.quantityDelta` (46), `StockReservation.quantity` (70), `OrderItem.quantity` (90) and prices (`catalog.prisma:117`) have no `CHECK` constraints. Postgres allows negative stock, zero quantities and negative prices.
**Why it matters**: AGENTS says "Stock cannot go negative through supported operations" and "no overselling". The atomic decrement lives in application code; a CHECK is cheap insurance against a future bug or manual SQL.
**Suggested fix**: Add hand-written `CHECK` constraints in the migration (`onHand >= 0`, `reserved >= 0`, `reserved <= onHand`, `quantity > 0`, `pricePoisha >= 0`, money `>= 0` where applicable). Prisma will not generate them, so add them explicitly and note it.

### 🟡 Missing indexes for obvious query paths, `prisma/schema/trust.prisma:50`
**Problem**: `SupportCase.assigneeUserId` has no index (support queue = "my assigned cases"), and `FinancialLedgerEntry.orderItemId` has no index although every sibling FK does (`payment.prisma:125-132`).
**Why it matters**: Spec task 8 explicitly says to review indexes for real query patterns. The support queue and per-item earnings/settlement lookups are both first-slice screens.
**Suggested fix**: Add `@@index([assigneeUserId, status])` on `SupportCase` and `@@index([orderItemId])` on `FinancialLedgerEntry`; check whether `Dispute.openedByUserId`/`Order.shippingAddressId` need the same.

### 🟡 Nothing enforces that exactly one first-party shop exists, `prisma/schema/seller.prisma:58`
**Problem**: `Shop.isFirstParty` is a plain boolean with a non-unique index (`seller.prisma:56-58`); two shops can be flagged first-party.
**Why it matters**: First-party shops are excluded from commission/seller liability. A second mistakenly flagged shop silently silences commission and payout accounting for its sales — a core financial boundary described in AGENTS.
**Suggested fix**: Add a partial unique index (`WHERE "isFirstParty" = true`) via raw SQL in the migration, or enforce single-row bootstrap semantics and document it; also specify that toggling `isFirstParty` is a super-admin audited action.

### 🟡 `FulfillmentStatus` mixes refund state into the fulfillment axis, `prisma/schema/enums.prisma:214`
**Problem**: `FulfillmentStatus` contains `REFUNDED`/`PARTIALLY_REFUNDED` (`enums.prisma:224, 228`), duplicating `OrderPaymentStatus.REFUNDED`/`PARTIALLY_REFUNDED` (`enums.prisma:237-238`), and it is also applied at item level (`order.prisma:96`) where `PARTIALLY_FULFILLED`/`PARTIALLY_CANCELLED` have no meaning.
**Why it matters**: AGENTS insists payment and fulfillment stay separate, but two fields can now both claim "refunded" and drift; item-level partial states are unrepresentable semantics that will produce invalid rows.
**Suggested fix**: Keep `RETURNED` as the terminal fulfillment outcome for returns and leave refund amounts/status to `PaymentStatus`/`Refund`/ledger; either use a separate item-level status enum or restrict order/shipment history to the states that make sense at that level.

### 🟡 Cross-shop attribution can drift between related rows, `prisma/schema/order.prisma:80`
**Problem**: `OrderItem.shopId`, `Shipment.shopId`, and `Listing.shopId` must agree, and an `InventoryBalance`/`StockMovement`/`StockReservation` may reference a `StockLocation` belonging to a different shop than the listing variant's shop; nothing in the schema prevents a mismatch (`order.prisma:80, 84`, `inventory.prisma:24-27, 41-44, 66-69`).
**Why it matters**: Seller commission, payout eligibility and shop-scoped authorization all key off `shopId`; a bad write attributes a sale to the wrong seller, which is exactly the accounting boundary the model is meant to protect.
**Suggested fix**: Document which `shopId` is authoritative (probably the shipment/order item's) and enforce agreement transactionally in checkout; add validation (and later a database trigger or composite FK) rather than relying on every future caller.

### 🟡 COD reconciliation resolutions are not attributable or linked, `prisma/schema/payment.prisma:175`
**Problem**: `CODReconciliationRecord` has `actorUserId`, `reason`, `evidenceRef`, and a mutable `status`, but no `resolvedAt`, no `resolvedByUserId`, no link from a resolved `SHORTAGE` to the `ADJUSTMENT` record that settled it, and no explicit adjustment-of-record reference.
**Why it matters**: D-32 requires a COD shortage to be resolved only by an explicit, reasoned, evidenced, audited adjustment, never auto-classified. The schema cannot prove that linkage; two records exist but nothing says which adjustment closed which shortage.
**Suggested fix**: Add resolution attribution (`resolvedAt`, `resolvedByUserId`) and a self-reference (e.g. `resolvesRecordId`) or an adjustment pair, and document that OPEN → RESOLVED requires it.

### 🟡 Schema tests are whitespace-coupled and do not exercise the database, `tests/marketplace-domain-model.test.ts:97`
**Problem**: The tests read the `.prisma` files as text and assert substrings that include exact alignment spaces (e.g. `"pricePoisha      Int"`, `"status           StockReservationStatus"`, `"eventKey           String                        @unique"`), are scoped per file rather than per model (several assertions can match a different model in the same file), and would pass even if the migration were wrong or missing. `verify.md:11` goes further and calls a nullable `FinancialLedgerEntry.shopId` proof of first-party exclusion, which it is not — a first-party shop can be stored in that column.
**Why it matters**: `prisma format` or a hand edit re-aligns columns and breaks dozens of assertions for no behavioural reason, and the suite currently locks the wrong money width (`Int`) while giving false confidence about AC-6. The real safety net for these constraints is the database.
**Suggested fix**: Assert per-model blocks (split the schema text per `model X { ... }` before matching) and match on normalized whitespace; drop the claim that a nullable `shopId` enforces first-party exclusion and test the exclusion rule where it will live (ledger posting). Once a test database is available, add a migration/constraint test (unique keys actually reject, cascades actually behave) instead of text matching.

## Nits

- ⚪ `prisma/schema/order.prisma:22`, `placedAt` and `createdAt` are always equal; pick one.
- ⚪ `prisma/schema/enums.prisma:14`, `RESUBMITTED` is not reachable in the spec's application flow (resubmission is described as a new application/review cycle); either model that or drop the value.
- ⚪ `prisma/schema/order.prisma:14`, `fxRateScaled` records a scaled rate without a recorded scale/exponent; define the scale as a constant or add `fxRateScale`.
- ⚪ `prisma/schema/trust.prisma:97`, `Dispute.resolvedAt` has no `resolvedByUserId`; the decision actor only exists in `AuditLog`.
- ⚪ `prisma/schema/order.prisma:10`, `shippingAddressSnapshot` is nullable even though checkout requires an address; a required snapshot would make the immutable-history intent explicit.
- ⚪ `prisma/schema/customer.prisma:45`, `ListingMedia` allows a row with neither `storageKey` nor `publicUrl`.

## Strengths

- The schema is split cleanly by domain with consistent `cuid` IDs, snake_case table maps, and comments, and the migration genuinely matches the schema (`prisma migrate diff` reports no difference; `migrate status` is up to date).
- Append-only intent is expressed structurally: `StockMovement`, `PaymentEvent`, `FinancialLedgerEntry`, `AuditLog`, and status histories have `createdAt` and no `updatedAt`, and `PaymentEvent.eventKey` / `StockReservation.idempotencyKey` are unique.
- Scope anchors are present on every protected record (`customerUserId`, `shopId`, actor refs), and private media (`SellerVerificationDocument.storageKey`, `ProofOfDelivery.mediaStorageKey`) is kept separate from public `ListingMedia.publicUrl` — matching the storage rules.
- Commission rates are stored as basis points with no invented default (`CommissionRule.rateBps` is required), which correctly leaves the pending policy to configuration instead of hard-coding a rate.
- The spec/verify pack is unusually concrete (independently checkable ACs, value-sourcing table, invariants) and the tests trace each AC.

## Test coverage

`npm run test` passes 35 tests with 11 skipped (the intentionally deferred T2–T7 gates), and `prisma validate`, `migrate status`, and a schema/database drift check all pass. The new schema tests cover presence of the expected models, fields, and a few constraints (one shop per owner, unique shop membership, one review per order item, event key uniqueness), which is reasonable as a bootstrap contract. Gaps: the assertions are text/whitespace-based and file-scoped (see Minor), they do not run against the migrated database so no constraint or cascade behaviour is actually tested, they lock in the `Int` money width, and nothing verifies the commission/discount snapshot fields that AC-6 depends on because those fields do not exist yet. Moving those assertions behind a real database test when the project's DB test harness lands would make the contract meaningful.
